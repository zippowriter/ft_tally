# テスト駆動開発

仕様と既存のテスト方法を確認し、次の順序で作業する。各ステップが終わるたびに、変更点と確認結果を伝え、次のステップに進んでよいか尋ねる。ユーザーの明示的な確認が届くまで、次のステップの実行やファイル変更を始めない。修正の指示が来たら現在のステップに反映し、再度確認を取る。

## ステップ1 — テストリストを作る

- 要件に対応する観測可能な振る舞いを、正常系、境界値、異常系にわたって列挙する。各項目は個別に検証できる粒度にする。仕様が未確定のケースは、確定済みの期待結果と区別して示す。
- リポジトリの `docs/tdd/{feature}/test_list.md` に、実施順の Markdown チェックリストとして保存する。既存のリストがあれば、進捗と機能名を引き継ぐ。

## ステップ2 — テストを1件書く（Red）

- 未完了の項目を1つ選び、リポジトリの既存の方式でテストを1件追加する。実行して、対象の振る舞いが未実装または誤っていることを理由に失敗するか確認する。
- 環境やテスト自体の問題で失敗した場合は、同じステップ内で原因を切り分ける。追加時点でテストが成功する場合は結果を報告し、既存の振る舞いを守る回帰テストとして扱う。失敗を作るために既存の実装を壊さない。

## ステップ3 — テストを成功させる（Green）

- 仕様に沿った最小限の実装を加え、追加したテストと関連する既存テストを実行する。すでに成功している項目はテスト結果を確認する。
- ステップ3の完了報告では、実装のどこをどう変更したか、その変更でなぜ期待どおりの振る舞いになるかを、テスト結果とあわせて簡潔に解説する。

## ステップ4 — 必要に応じてリファクタリングする

- 改善が必要なら、振る舞いを保ったまま関連コードを整理し、テストを再実行する。変更が不要なら、その判断を伝える。

## ステップ5 — リストを更新する

- 完了した項目にチェックを入れ、残りの項目数を伝える。残りがあれば、確認を得てステップ2に戻る。残りがなければ、テスト結果とともに完了を報告する。
